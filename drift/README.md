# Drift suite

[Drift](https://support.smartbear.com/swagger/contract-testing/docs/en/drift.html)
replays a set of operations against a running Pact Broker and validates every
response — status code, headers, body — against an OpenAPI document.

`openapi.json` here is **not** hand-written and does not describe this
implementation. It is generated by
[pact_broker-rs](https://github.com/you54f/pact_broker-rs) from its own route
definitions (`cargo run --example dump_openapi`), and copied here along with the
`drift.yaml` and `pact_broker.lua` that drive it there. Running it against the
canonical Ruby broker turns every failure into a concrete, reproducible
divergence between the two.

Current state: **113 of 113 operations pass**, here and in pact_broker-rs,
against the same generated `openapi.json` and the same `drift.yaml` — no
curation step in between. This broker is canonical: every divergence the suite
found was resolved by changing pact_broker-rs, never by editing the spec to
describe something this broker does not do. What was reconciled, and how, is
recorded below.

## Running it

Requires the `drift` binary on `PATH` (see the link above for installation).

```
bundle exec rake drift
# or
bundle exec ruby drift/run.rb
```

`run.rb` boots `drift/config.ru` under **Puma** on port 9292 against a throwaway
SQLite database, waits for the heartbeat, shells out to `drift verify`, and
exits with Drift's exit code. Reports land in `drift/output/` (git-ignored): a
JUnit XML report under `reports/`, and a machine-readable `results/*.result`
with the per-operation detail.

Puma is not optional, which is why it is in the Gemfile's development group.
WEBrick cannot run this suite: it answers `411 Length Required` to the bodyless
writes Drift sends, and a second read of a request body comes back empty, which
breaks every write operation.

`openapi.json` is copied verbatim from pact_broker-rs's repo root; refresh it
from there rather than editing it here. `drift.yaml` is likewise a copy of that
repo's `tests/drift/drift.yaml`, differing only in the `sources[].path` to the
spec, which sits beside this file here and two levels up there.

Environment variables:

| Variable | Default | |
| --- | --- | --- |
| `DRIFT_SERVER_PORT` | `9292` | port the broker listens on and Drift targets |
| `DRIFT_LOG_LEVEL` | `error` | Drift's own log level; `debug` shows the Lua hooks |
| `DRIFT_APP_LOG_LEVEL` | `warn` | the broker's log level |
| `DRIFT_DATABASE_PATH` | `tmp/drift.sqlite3` | deleted and recreated on every boot |

To drive it by hand, boot the app on its own and run the CLI yourself:

```
bundle exec puma drift/config.ru -p 9292
DRIFT_PACT_BROKER_URL=http://localhost:9292 \
  drift verify --test-files drift/drift.yaml --server-url http://localhost:9292
```

## How state is set up

Each operation needs the database to hold exactly the rows its request needs,
and nothing else. `pact_broker.lua` hooks Drift's operation lifecycle and calls
two test-only routes that `test_state.rb` mounts as middleware in front of the
real app:

- `POST /test/setup/{operationId}` — seeds the database for that one operation
  via `PactBroker::Test::TestDataBuilder`, and answers with the values the
  seeding *generated* rather than chose (UUID primary keys, the pact-version
  SHA). `drift.yaml` reads those back out through `${functions:...}`, since it
  cannot hardcode them.
- `POST /test/reset` — truncates the database, so operations don't see each
  other's state.

The key passed to `/test/setup` is the **testcase key** in `drift.yaml`, not the
`operationId` it targets — which is why a testcase repointed at another
operation (see below) keeps its original key.

The `when` branches in `test_state.rb#seed` are a direct port of `seed_state`
in pact_broker-rs's `tests/drift.rs`, kept in the same order and with the same
groupings so the two can be diffed when `drift.yaml` changes. An operation key
with no branch answers `400`, rather than silently running against an empty
database.

## Resolved: schemas pact_broker-rs documented wrongly

Each was a place the Rust broker documented — and served — a response this one
does not; all six were changed there, so the column on the right is what both
brokers now render.

| Schema | The spec used to say | Both brokers now render |
| --- | --- | --- |
| `EnvironmentResponse` | `updatedAt` required | `updatedAt` only when it differs from `createdAt`, per the `Timestamps` decorator |
| `WebhookResponse` | `updatedAt` required | `updatedAt` only when it differs from `createdAt`, per the `Timestamps` decorator |
| `WebhookListResponse` | `_embedded` required | `_links` alone, with the webhooks as a `_links.pb:webhooks` array of link objects |
| `BranchVersion` | `branch` required | `{ "name": "main", "latest": true, "_links": … }` — the branch name is under `name`, and `latest` says whether the version is the branch head |
| `MatrixParticipant.version` | non-nullable object | `null` for a provider that hasn't verified the pact, as `CanIDeployParticipant` already documented |
| `MatrixVersion`, `CanIDeployVersion` | no `branches` property | `branches` alongside `branchVersions`, with identical contents |

## Resolved: routing and status-code divergences

**Routes pact_broker-rs served that this one does not.** These answered `404`
here. They were Rust-only additions, so they were removed there and their
testcases deleted; the suite went from 121 operations to 113.

| Operation | |
| --- | --- |
| `list_all_verifications` | `GET /verifications` |
| `list_provider_verifications` | `GET /verifications/provider/{provider}` |
| `list_tags` | `GET /pacticipants/{name}/versions/{version}/tags` |
| `list_pact_version_webhooks`, `create_pact_version_scoped_webhook` | `/webhooks/provider/{p}/consumer/{c}/pact-version/{sha}` |
| `delete_deployed_version`, `delete_released_version` | `DELETE` on a deployed/released version — not deletable here; recorded undeployed/unsupported instead |

`GET /pacticipants/{name}/network` was also removed from pact_broker-rs's API.
Both brokers still serve that path as an HTML UI page; only the JSON
representation, which this broker never had, is gone.

**Same resource under a different operation.** Five testcases were repointed at
the operation both brokers actually serve, and the Rust-only operation deleted.

| Testcase | Used to target | Now targets |
| --- | --- | --- |
| `create_version` | `POST /pacticipants/{name}/versions` | `PUT /pacticipants/{name}/versions/{version}` |
| `create_branch` | `POST /pacticipants/{name}/branches` | `PUT /pacticipants/{name}/branches/{branch}/versions/{version}` |
| `list_groups` | `GET /groups` | `GET /groups/{name}` |
| `list_labels` | `GET /pacticipants/{name}/labels` | `GET /labels` |
| `get_integration` | `GET /integrations/provider/{p}/consumer/{c}` | `DELETE` on the same path — `Integration#allowed_methods` is `["OPTIONS", "DELETE"]` |

**`publish_pact`.** Its annotation in pact_broker-rs declared both `PUT` and
`POST`, and only the last won, so the spec said `POST`; it now says `PUT`, as
this broker requires. Its response schema was the contract-publication report
(`logs`, `notices`, `_embedded`), which belongs to `POST /contracts/publish`.
`Api::Resources::Pact` renders the pact itself on a write, via `PactDecorator`
— the same body a `GET` of that resource returns — and pact_broker-rs now does
too.

**Content-type strictness** (`415`): `create_tag`, `create_label`,
`record_release_for_version`, `create_branch` and `execute_saved_webhook` are
writes Drift sent with no request body at all. This broker requires a
`content-type` on a write regardless. Each of those testcases now declares
`request: body: {}`, which makes Drift send the header, and the corresponding
operations in the spec document an empty-object request body.

**Required query parameters**: `fetch_matrix` answered `500` for a bare
`GET /matrix`. Drift cannot serialise an array-of-objects query parameter into
Rack's bracket notation, so the selectors are now declared in the spec under
their literal names — `q[][pacticipant]`, `q[][version]`, `q[][latest]` — and
the testcase passes one.

**Stricter preconditions**: `execute_saved_webhook`
(`POST /webhooks/{uuid}/execute`) answers `400` here for a webhook with no pact
behind it, so its testcase seeds a published pact.

**Default representation**: `GET /integrations` defaults to `text/vnd.graphviz`
here and only renders the documented HAL body when asked for it;
pact_broker-rs serves HAL either way. Worked around in `drift.yaml` with an
explicit `Accept: application/hal+json`.

## Known parity gaps the suite does not catch

Schema-compatible differences in the two brokers' bodies, recorded for whoever
is reconciling them:

- this broker's `pb:pact-version` href carries a `/metadata/…` segment that
  pact_broker-rs omits;
- pact_broker-rs emits `mainBranch` and `repositoryUrl` on pacticipants, and
  `updatedAt` on pacticipant list items, that this broker does not;
- `WebhookDecorator` here has a `pb:webhooks` link that pact_broker-rs's
  single-webhook body omits;
- for the scalar `branch`, this broker takes `branch_versions.last`,
  pact_broker-rs takes the first.
